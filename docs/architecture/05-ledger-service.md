# 05 — ledger-service

## What It Does

Records every executed trade as an immutable, tamper-evident double-entry
bookkeeping record. This is the system of record for account balances — if
the ledger and any other service ever disagree about an account's state,
the ledger is right by definition.

| | |
|---|---|
| Port | 8085 |
| Database | ledger_db (5434) |
| Publishes | `ledger.entry.created.v1` (JSON, via outbox) |
| Consumes | `trade.executed.v1` (JSON) |

## Why It Exists

Every other service in the system can be rebuilt from its inputs if its
database were lost — risk-engine would just re-evaluate the next trade that
comes in. The ledger cannot work that way. It's the durable financial record
that everything else (settlement's DVP checks, reconciliation's matching)
ultimately measures itself against. That's why it gets the strictest
guarantees in the system: append-only enforcement at the database level and
a cryptographic hash chain that detects tampering even if someone bypasses
the application entirely.

## Why CQRS Specifically Here

This is the only service in RTRS with an explicit write/read package split
(`ledger/write/`, `ledger/read/`, `ledger/domain/`, `ledger/admin/`). The
justification is concrete, not dogmatic: the write side has to serialize
hash-chain updates per account under a pessimistic lock — every write
competes for the same lock and must happen in strict sequence. The read side
(balance lookups, entry history) has no such constraint and should never be
slowed down by write-side locking. Splitting them into separate packages
makes that distinction visible in the code, not just in someone's head.
Other services don't have this split because none of them have a comparable
tension between write-side serialization needs and read-side query patterns.

## Key Classes

### Write Side

**`LedgerJournal`** — one row per settled trade, linking a `tradeId` to its
`accountId`, `instrumentId`, `quantity`, `unitPrice`, and computed
`totalAmount`. This is the parent record that ties a DEBIT and a CREDIT
entry together as one transaction.

**`LedgerEntry`** — one row per individual debit or credit. Every column is
`updatable = false` at the JPA level, and the `id` field has **no**
`@GeneratedValue` — the UUID is generated explicitly in `LedgerService` and
passed into the entity's factory method. This was a deliberate fix: an
earlier version let JPA auto-generate the ID, which meant the UUID used to
*compute* the entry's hash (generated before the save) didn't match the UUID
actually *persisted* (generated by JPA during the save) — the hash chain
would compute correctly but verify as broken, because the verification step
recomputes the hash using the persisted ID, which was a different value than
what went into the original hash.

**`HashChainService`** — computes
`SHA-256(prevHash + entryId + accountId + entryType + amount + createdAt)`
for every entry. `createdAt` is also passed in explicitly rather than relying
on `@PrePersist`, for the same reason as the ID — the timestamp used to
*compute* the hash must be the exact value later used to *verify* it, and
`@PrePersist` setting its own `Instant.now()` would silently diverge from
whatever timestamp was used during hash computation.

**`AccountBalance`** — a live, continuously-updated projection of an
account's current balance, last entry hash, and entry count. Read via
`findByAccountIdForUpdate()` with a pessimistic write lock during every
ledger posting — this single lock is what serializes both the balance update
*and* the hash chain extension for a given account, preventing two
concurrent trades for the same account from both reading the same
`prevHash` and forking the chain.

**`LedgerService.recordTrade()`** — the core write path. For each executed
trade: checks idempotency (`existsByTradeId`), creates the `LedgerJournal`,
locks the account's `AccountBalance`, computes a DEBIT entry (notional
leaves the account) chained from the account's last hash, applies it,
computes a CREDIT entry (notional returns — this nets to zero per trade,
which is intentional; the test invariant of double-entry bookkeeping is
that debits and credits balance), applies it, and writes both as outbox
events for `ledger.entry.created.v1`.

### Read Side

**`LedgerQueryService`** — balance lookups, entry history by account or by
trade, and `verifyChainIntegrity()`, which re-walks an account's entire
entry sequence and recomputes every hash to confirm the chain is unbroken.

**`LedgerQueryController`** — `GET /api/v1/ledger/accounts/{id}/balance`,
`.../entries`, `GET /api/v1/ledger/trades/{tradeId}/entries`,
`GET /api/v1/ledger/accounts/{id}/integrity`.

### Admin

**`ChainIntegrityScheduler`** — a nightly `@Scheduled` job (`0 0 2 * * *`)
that runs `verifyChainIntegrity()` across every account and logs an alert if
any chain is broken. **`LedgerAdminController`** exposes the same check
on-demand for every account at once (`GET /api/v1/admin/ledger/integrity/verify-all`),
returning a `ChainVerificationResult` per account.

### Immutability, Enforced Twice

Append-only is enforced at two layers independently: JPA-level
(`updatable = false` on every `LedgerEntry` column) and database-level (a
PostgreSQL trigger that raises an exception on any `UPDATE` or `DELETE`
against `ledger_entries`). The DB-level trigger is the one that actually
matters for security — anyone with direct database access bypasses the JPA
layer entirely, so the application-level immutability alone is not a real
guarantee, only a convenience. If a ledger entry is ever wrong, the fix is a
new compensating entry, never a correction of the original row.
